dsh-verifier-brain 迭代计划（ITERATION PLAN）评审意见
文档版本：v1.0（基于 ITERATION_PLAN.md 2026-08-21 版本）
评审日期：2026-08-21
评审人：技术顾问
总体结论：通过，建议按以下意见微调后实施

一、总体评价
这是一份高质量的迭代计划，核心亮点在于：

问题驱动：所有改动都来自实战中“被噪声咬伤”的真实案例（LRU、马里奥、111.txt），说服力强，避免了“为了加功能而加功能”的陷阱。

成本意识：不搞“全局 K=3”一刀切，而是通过自适应升级将期望成本增幅控制在 <1.5×，非常务实。

边界清晰：第六节“明确不做”有效防止了范围蔓延，保证了本次迭代的可交付性。

验收可量化：7 条验收用例全部可执行，不是泛泛而谈。

在现有基础上，以下 6 个方面的细节值得在编码前进一步明确。

二、详细评审意见与建议
2.1 缓存键设计需加入 n_evaluations 维度
原文引用：

“绕过缓存，缓存键加入 k”

潜在风险：
如果缓存键仅包含 (候选内容, 标准, 模型)，K=1 的首次结果将被 K=3 的升级结果覆盖。这在后续审计或分析“首次评分 vs 升级后评分”的差异时会丢失原始数据。

建议方案：

缓存键中显式加入 n_evaluations 字段，使 K=1 与 K=3 的结果并存。

返回结果中增加 cached: true/false 字段，明确告知用户当前结果是实时计算还是命中缓存。

2.2 “方向不一致”的报告逻辑需细化判定规则
原文引用：

“方向不一致时……如实报告‘信号不稳定，建议人工复核’，不许静默取平均了事。”

潜在风险：
“方向不一致”在 compare 和 select 两种模式下的表现不同，判定规则若未提前定义，开发时可能产生歧义。

建议方案：

场景	判定规则	输出行为
Compare（3次）	3次中胜者全部一致 → 一致	取平均分，标注“3/3 一致”
3次中胜者 2:1 → 微弱一致	取平均分，标注“2/3 一致，建议谨慎参考”
3次中胜者 1:2 → 不一致	不取平均，返回全部 3 组原始分数，标注“信号不稳定，建议人工复核”
Select（3次）	3次中第一名全部相同	取平均排名/分数
3次中第一名不一致	不取平均，返回 3 次独立排名，标注“第一名不一致，建议人工复核”
2.3 异步任务降级至 K=2 时的位置偏差问题
原文引用：

“触界时自动降级为 K=2 并在结果中注明”

潜在风险：
官方 llm-as-a-verifier 的“位置偏差抵消”机制依赖于奇数轮交替 A/B 槽位。K=2 时不发生交替，位置偏差可能重新污染评分结果。

建议方案：

在降级至 K=2 时，于输出结果中强制添加醒目标注：

“⚠️ 因超时降级为 2 次评估，位置偏差可能未被完全抵消，结论可信度低于 K=3。”

若后续有精力，可研究 K=2 场景下手动强制交换一次槽位（需确认官方 API 是否支持），否则接受此限制并在文档中说明。

2.4 “触界”的定义需明确
原文引用：

“触界时自动降级为 K=2”

潜在风险：
“触界”是指接近 taskTimeoutMs（整体任务超时），还是指单次评分调用已耗时超过阈值？定义模糊将导致实现时难以决策。

建议方案：
在 src/tools.ts 中设置一个内部水位线：

若 剩余超时时间 < 预估升级耗时 × 1.2，则触发降级。

预估耗时可基于历史平均单次评分耗时（如 3-5 秒/次）动态计算。

将此逻辑在代码中显式实现，并记录降级原因到日志。

2.5 证据链自动化中“冒烟测试”的泛化范围
原文引用：

“冒烟工具从‘马里奥专用’泛化为通用 HTML/JS 产物校验器”

潜在风险：
不同候选产物的运行形态差异巨大（自执行 HTML、Node.js 脚本、React 构建产物等）。过早追求“全泛化”可能导致 M3 阶段工作量失控。

建议方案：
将 M3 阶段的“泛化”限定在以下两种核心类型，其余标记为“实验性”：

HTML 文件：使用 Playwright/CDP 打开，采集控制台错误 + 截图。

Node.js 脚本：使用 child_process 执行，采集 stdout/stderr + 退出码。
在文档中明确列出当前支持的产物类型，避免用户期望过高。

2.6 与 dsh-agent-teams 的集成时机
原文位置：
第六节“明确不做”中提到“与 agent-teams 合并已论证”。

建议方案：

本次迭代（M1+M2）：暂不进行代码级集成。专注于让自适应 K 机制在验证层站稳。

集成时机：待自适应 K 稳定运行 1-2 周后，在 dsh-agent-teams 的“评审员 (reviewer)”角色 system prompt 中，注入一条提示：

“调用 verifier 时使用默认配置即可，系统会自动根据分差升级评估次数。”
这样无需修改 dsh-agent-teams 代码，即可让整个团队共享验证层的可信度提升。

三、建议补充的验收用例
除计划中已有的 7 条外，建议增加以下 3 条，以覆盖上述风险点：

#	用例	期望
8	select N=5，所有候选分差接近	自动升级 K=3，总耗时在可接受范围内；若超时，降级 K=2 并附标注
9	升级后结果被缓存，再次调用相同候选	直接命中缓存返回（含升级元数据），不重复调用 API
10	3 次评估中第一名不一致（构造含噪声候选）	返回“信号不稳定”+ 3 组原始排名/分数，不静默取平均
四、实施优先级建议
优先级	内容	说明
P0（必须）	缓存键加入 n_evaluations	防止数据丢失
P0（必须）	方向不一致判定规则明确化	避免实现歧义
P1（强烈建议）	K=2 降级标注位置偏差风险	维护结果可信度
P1（强烈建议）	冒烟测试泛化范围收窄	控制 M3 工作量
P2（可延后）	与 agent-teams 集成时机确认	目前不紧急
五、最终结论
当前计划整体成熟可行。建议在编码开始前，将上述 P0 级建议（缓存键设计、方向不一致判定）落实到 src/tools.ts 的设计中，P1 级建议在实现时保持关注即可。

M1+M2 完成后发布的 v0.2.0 版本，将有效解决“分数不可信”的核心痛点，为后续证据链自动化和 /bestofn 命令打下坚实基础。
